# SentiLight — Policy-Space Reformulation for Affective Smart-Lighting Control

[![DOI](https://zenodo.org/badge/DOI/10.5281/zenodo.21930495.svg)](https://doi.org/10.5281/zenodo.21930495)

Research artifacts for a study of output-formulation versus model scale in a smart-lighting
control task governed by a finite policy.

This repository contains the code, evaluation data, per-row predictions and preregistrations
needed to **recompute every reported number**. Model weights are distributed separately
(see [Model weights](#model-weights)).

---

## The task

Enumerating the deterministic labelling policy over {no colour + 7 colours} ×
{no emotion + 5 emotions} × {5 intensities} yields exactly **K_eff = 240** reachable
(H, S, B, Dimmer, CT) tuples. The question is whether reformulating the model's output from
free-form JSON generation to classification over that finite action space buys more than
increasing model size does.

Five model families are compared at three seeds each on a 1,000-row rule-based evaluation
segment:

| Family | Params | Strict | Coarse |
|---|---:|---:|---:|
| A1 generative LM 23M | 23,378,304 | 38.57% ± 3.27 | 64.47% ± 4.96 |
| generative LM 60M | 62,112,256 | 42.43% ± 3.06 | 67.03% ± 4.24 |
| A2 policy-only LM 23M | 23,378,304 | 49.30% ± 1.28 | 78.80% ± 2.01 |
| **B2 tuple head 23M** | 23,470,464 | **51.23% ± 2.14** | **84.67% ± 1.75** |
| tuple head 60M | 62,235,136 | 51.03% ± 4.99 | 81.83% ± 6.79 |

Trivial baselines on the same segment. The one to compare against is the strongest, not the
weakest:

| Baseline | Strict | Coarse |
|---|---:|---:|
| Uniform random over the 240 tuples | 2.03% | 5.94% |
| Train-majority tuple | 3.00% | 3.30% |
| SBERT nearest prototype | 4.70% | 10.30% |
| **Best constant tuple** | **9.90%** | **17.80%** |

## Caveats that travel with the data

These are not fine print. Anyone reusing these artifacts needs them.

1. **The natural-language segment is contaminated and is not an evaluation set.** All 1,000
   of its inputs appear verbatim in the pretraining corpus. It is released as a diagnostic
   only. The rule segment is the benchmark and is clean: zero residual overlap under exact,
   normalized and 13-gram Jaccard ≥ 0.8 checks, with a maximum corpus Jaccard of 0.182.
2. **Accuracy here means policy compliance, not perceptual quality.** The reference is the
   deterministic policy itself, so the metric is circular with respect to human preference.
3. **Latency figures are not an optimized-decoder benchmark.** The generative path has no KV
   cache and never early-stops. Under one protocol (batch 1, CUDA-synchronized, warm-up
   discarded) the classification head takes 2.01 ms and the 60M generative model 378.49 ms.
   The implementation-independent statement is one forward pass versus 96 — about 31 with
   working early stopping.
4. **Natural-row labels were produced by Gemini 2.5 Flash Lite**, so any comparison against
   Gemini is teacher–student and must say so.
5. **The tokenizer was derived from the pre-purge corpus and frozen** (its training script
   was not preserved), so a second-order trace may remain in the subword vocabulary.
6. **The 240-way tuple head is not part of the deployed five-model system.** Deployment
   demonstrates real actuation; the controlled comparisons are offline.

```
  server/                FastAPI /predict_all
  models/compact_llm/    model definition, tuple classifier, tokenizer, datasets
  qwen_service/          comparator: LoRA-SFT code, data and adapter

```

## Reproducing the numbers

Requires Python 3.10+, PyTorch and `tokenizers`. Everything below runs on CPU from this
repository alone; only the training and latency drivers need a GPU and the separately
distributed weights.

```bash
# row-level adjudication: exact McNemar -> Stouffer across seeds -> Holm over the
# preregistered contrast family
python tools/run_row_level_tests.py

# per-stratum decomposition of those contrasts
python tools/source_stratum_decomposition.py

# constrained-decoding control: nearest-tuple projection of generative outputs
python tools/run_projection_control.py

# contamination-delta comparison across the paired grids
python tools/compare_contamination_delta.py --out results/contamination_delta_results.json

# trivial baselines and the per-dimension failure decomposition
python tools/recompute_trivial_baselines.py
python tools/decompose_strict_failures.py

# contrasts under the three backbone conditions
python tools/recompute_c1_c2_fully_clean.py

# figures
python tools/make_figures.py

# consistency guard: the canonical spec against the scorer of record
python tools/check_lighting_spec_consistency.py
```

Outputs land in `results/`. Figure 4 additionally needs `tools/run_latency_measurement.py`, which
requires a GPU and the checkpoints; `make_figures.py` skips it and reports why if the
latency measurements are absent.

## Preregistration

Four protocols were written and hash-committed **before** the corresponding results were
computed. `preregistration/SHA256SUMS` lets anyone verify the files are unmodified:

```bash
cd preregistration && sha256sum -c SHA256SUMS
```

| Protocol | Fixed in advance |
|---|---|
| `prereg_contamination_delta.md` | four predictions about the effect of purging the pretraining corpus |
| `prereg_teacher_consistency.md` | the criteria for withdrawing a planned analysis path |
| `prereg_w1_contrast_family.md` | the contrast family (m = 8), the test procedure and the adoption rule |
| `prereg_w2_constrained_decoding.md` | the projection metric and the decision thresholds |

`eval_split_freeze.json` records the frozen evaluation splits.

Three of the four contamination predictions did not hold, and they are reported as misses
rather than revised. The row-level protocol explicitly predicted that one contrast would be
dropped; the data went the other way. Both outcomes stand as written.

`preregistration/PROVENANCE.md` records, for each protocol, the commit that introduced it and
the commit that recorded the corresponding result, with timestamps — the digests alone show
only that the files are unmodified, not when they were written. It also states the limits of
that evidence.

> The protocols reference internal working documents that are not part of this release, so
> those links do not resolve here. The files are left exactly as written: editing them to
> tidy the links would change their digests and break the tie to the commits.

## Model weights

Checkpoints for the five families at three seeds, the merged comparator model and the
GGUF exports total about 6.8 GB and are distributed separately.

They are not needed to verify the analysis: per-row predictions and run summaries for all
36 clean and 36 contaminated grid cells are in `backend/reports/`, and every statistic and
figure is computed from those.

## Excluded from this release

- Human-participant survey materials, in full. The study is purely computational and no
  survey data, claims or artifacts are released.
- Model weights and optimizer states.
- The live deployment configuration, which carries host and bulb addresses.
  `backend/config/models.example.yaml` shows the schema.

## A note on paths in the records

Run summaries and dataset manifests record where each artifact came from. Those paths have
been rewritten from the producing machine's absolute layout to repository-relative form; no
digest published here covers those files, so nothing is invalidated by the change.

Where an artifact originated in an earlier working tree rather than this one, the path is
marked `<prior-tree-v4>/…` instead of being silently rewritten to look local. Sources outside
the project appear as `<external>/…`. Nothing in the analysis depends on any of these paths:
every script resolves locations relative to the repository root.
